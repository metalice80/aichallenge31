Построение с пустым кешем стало **в 8,46 раза дольше**, прибавка **354,84 с (5 мин 55 с)**. С учётом подготовки данных прибавка до готовности RAG — 366,24 с. Почти всё время первичного построения приходится на реальные запросы BGE-M3. Увеличение числа файлов в 12,5 раза не означает такой же рост числа векторов: длина файлов различается, одинаковые фрагменты дедуплицируются.

Кешированный повтор на неизменном SHA не вычисляет embeddings заново, но штатный pipeline всё равно получает метаданные PR, выполняет поиск и читает выбранные файлы через MCP. Поэтому 0,297 с — время работы индексатора с готовым снимком, а не всего ревью. При следующем commit индекс пересобирается для нового SHA с переиспользованием неизменённых embeddings; именно такой переход в этом замере отдельно не измерялся. Расширение существующего кеша runner с 80 до 1000 также отдельно не измерялось: результаты «с нуля» получены в изолированных пустых кешах.

Все четыре настоящих локальных ревью завершились с 0 замечаний и статусом `partial`: 1000 файлов всё ещё меньше 2336 разрешённых файлов снимка, а отдельный текстовый поиск ограничен 500 файлами/12 результатами. Это измерение производительности, не доказательство улучшения качества поиска или ревью.

Параметры: `bge-m3:latest`, `qwen3:8b`, `chunk_chars=1400`, `overlap_chars=160`, `batch_size=8`. Digest моделей и точные времена находятся в JSON. Модели и лимиты контекста/поиска не менялись. Список 80 файлов входит в список 1000; хеши источников холодного и повторного запуска совпадают. Исходный Outline остался на прежней ветке/SHA с чистым Git status. Никакие комментарии или изменения в GitHub во время этого замера не публиковались.

Проверки изменения: **49 автоматических тестов прошли за 12,98 с**, `pip check` успешен, `git diff --check` без ошибок. Автоматические тесты используют фикстуры моделей/API; приведённые выше измерения используют настоящие сервисы.

## Методика

- Настоящий открытый PR #1 в `metalice80/outline_t`, один head SHA для всех запусков. GitHub API только читается, публикация отключена.
- Штатный `run_review`: настоящий MCP stdio, изолированный Git-снимок, штатный отбор источников, Tree-sitter, BGE-M3 через Ollama и SQLite/NumPy. Анализ Qwen3 8B также настоящий, но его время не включается в время построения индекса.
- Два независимых пустых кеша: 80 файлов и 1000 файлов. Затем повторный запуск каждого с тем же кешем и SHA. Имеющийся кеш runner не очищается и не используется в измерении.
- «Пустой кеш» означает пустые кеш эмбеддингов и индекс снимка. Git и кеш ОС не очищаются. BGE-M3 прогревается отдельным запросом перед каждым замером; время прогрева записывается отдельно.
- `index_seconds`: реальный `ReviewIndex.update_sources`, включая разбиение, чтение кеша, embeddings, запись и загрузку поколения индекса. `embed_seconds`: только запросы Ollama с эмбеддингами источников внутри индексации. `pre_index_seconds`: подготовка до вызова индексатора, включая MCP/API/Git, поиск и чтение файлов. `review_seconds`: весь локальный `run_review`, включая индекс, поиск и Qwen.
- Используется подкласс только для таймеров; результаты индексации, Ollama, MCP и GitHub не подменяются. Код основных модулей совпадает с установленным пакетом runner.
- По одному запуску каждого варианта: это наблюдение на данном компьютере и PR, не статистическая оценка. Фоновая нагрузка и кеш ОС могут влиять на результат. Проверяется вложенность корпусов 80 ⊆ 1000 и совпадение хешей источников между первым и повторным запуском.

## Воспроизведение

Из корня проекта, с доступными Ollama и GitHub и открытым PR #1:

```bash
.venv/bin/python evaluation/day32/benchmark_index.py > evaluation/day32/index-benchmark.log 2>&1
```

Скрипт читает настройки `/Users/sergey/ai/outline-review-runtime/config.toml`, принудительно отключает публикацию и создаёт отдельные кеши в `.review-cache/index-benchmark/run-*`. Каждый новый вызов начинает сравнение с пустыми кешами эмбеддингов; результаты этого каталога перезаписываются. Крупные кеши игнорируются Git. Путь текущего кеша, SHA, параметры, digest моделей, времена и списки файлов записаны в [results.json](results.json); полные локальные отчёты — в подкаталогах `80-cold`, `1000-cold`, `80-warm`, `1000-warm`.
