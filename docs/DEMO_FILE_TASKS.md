# Ручное демо: поиск использований и обновление документации в Outline

Оба сценария выполняются в существующем `/Users/sergey/ai/aichallenge/outline`. Клонирование, временные проекты и установка второго ассистента не нужны. Ассистент запускается из `aichallenge31`, а читает и изменяет проект из `repo_path` его конфигурации. Продолжительность показа — примерно 15–20 минут с запасом на ответы Qwen3 8B.

План содержит действия для будущего ручного показа. При его подготовке код и Git-состояние Outline не изменялись. GitHub, runner, commit и push для этих двух сценариев не нужны. Демонстрация PR описана [отдельно](DEMO.md).

**Статус после ручной проверки:** для ближайшего показа первый сценарий сужен до прямых импортов `shallowEqual`. Этот вариант дал корректный результат в настоящем dry-run; точный запрос и критерии приведены ниже. Полный анализ всех вызовов на Qwen3 8B по-прежнему не подтверждён: прежние попытки давали `partial`, ложный `no_changes` либо неполный отчёт. Подробности и все попытки — в [разборе пользовательского запуска](../evaluation/day34/usage-demo-fix/REPORT.md).

В текущей конфигурации `repo_path` уже указывает на этот Outline, используются `qwen3:8b` и `bge-m3`. Ollama должна работать; MCP запускается автоматически. Каталог запусков по умолчанию — `.task-runs` в проекте ассистента. Если задавали другой `task_runs_dir`, укажите его абсолютный путь в `DEMO_RUNS`. Используйте бинарник текущего проекта: установленный `outline-review-runtime` в рамках Day 34 не обновлялся.

Начните показ с чистого рабочего дерева Outline. Если `status --short` показывает ваши незавершённые изменения, сначала отдельно сохраните или завершите их; не выполняйте автоматический reset/clean. На момент подготовки плана дерево было чистым. Запишите текущую ветку, затем создайте демонстрационную ветку **в этой же рабочей копии**:

## 2. Найти прямые импорты API — проверенный упрощённый вариант, 3–5 минут

**Что сказать:** «Ассистент сам найдёт файлы, прямо импортирующие shallowEqual, прочитает исходники и подготовит таблицу в существующей документации».

Для Qwen3 8B цель сужена до прямых импортов с написанием `import shallowEqual`. Полный перечень вызовов, алиасы и реэкспорты этот вариант не проверяет. Он показывает реальный поиск, чтение, RAG и подготовку документа. В исходном полном сценарии модель продолжала ошибаться; упрощение не считается исправлением всех этих ограничений.

Точная проверенная формулировка сохранена в [direct-imports.txt](../evaluation/day34/prompts/direct-imports.txt). Она задаёт короткие чтения и простой якорь редактирования: первая строка `# Architecture`. Модель получает имя API и целевой документ; пути файлов-потребителей в запрос не подставлены.

```bash

  "$(cat "$DEMO_ASSISTANT/evaluation/day34/prompts/direct-imports.txt")"
```

Ожидается `prepared`. Скопируйте новый ID из вывода:

Проверьте таблицу:

| `app/hooks/useActionContext.tsx:5` | `import shallowEqual from "@shared/utils/shallowEqual"` |

В текущем снимке это два прямых импорта. Сверьте строки с реальными файлами:


Откройте `events.jsonl`: должны быть `search_text`, успешное чтение обеих строк импорта, `search_context`, чтение заголовка документа, `propose_file_change`, `preview_changes`, `finish_task`. Чтения всего документа здесь не требуется: замена касается только прочитанной первой строки, остальной текст сохраняется по точному совпадению и хешам.

В diff должен появиться раздел `## ShallowEqual imports` сразу после `# Architecture`, **вне блока кода**. Проверьте сохранность остального документа. Сам `prepared` не заменяет эту проверку.

Это один успешный реальный прогон, не гарантия каждого повторения. Для первого сценария **не выполняйте apply-run**: покажите подготовленный diff, чтобы перед вторым сценарием Outline оставался чистым. Уже сохранённый удачный пакет можно показать как архивный результат, явно назвав его так.

## 3. Внести небольшое изменение кода — 2 минуты

**Что сказать:** «Теперь меняю поведение приложения, а описание пока оставляю старым. Ассистент должен сам найти документацию, которую затрагивает изменение».

В редакторе откройте `outline/server/main.ts`. В блоке установки middleware замените ровно одно условие:

Было:

```ts
if (env.DEBUG.includes("http")) {
  app.use(logger((str) => Logger.info("http", str)));
}
```

Стало:

```ts
if (env.isDevelopment || env.DEBUG.includes("http")) {
  app.use(logger((str) => Logger.info("http", str)));
}
```

Смысл: в development HTTP middleware подключается по умолчанию, в остальных окружениях сохраняется проверка `DEBUG`, содержащего `http`. `env.isDevelopment` определяется через `NODE_ENV === "development"`. Фильтрация сообщений уровнем `LOG_LEVEL` остаётся прежней.

Сохраните файл, **README вручную не меняйте**. Покажите исходный раздел `README.md → Debugging`: он всё ещё говорит, что HTTP logging выключен по умолчанию. Проверьте, что diff содержит только задуманную правку:

```bash
git -C "$DEMO_OUTLINE" diff -- server/main.ts
git -C "$DEMO_OUTLINE" status --short
```

Не коммитьте это изменение перед следующей командой: по умолчанию ассистент сравнивает HEAD с рабочей копией, включая staged и unstaged. Если изменение уже закоммичено, потребуется `task --base <SHA_до_изменения> ...`.

Это учебное изменение для демонстрации анализа кода; запуск сервера Outline и проверка реального HTTP-трафика в этот план не входят.

## 4. Обновить документацию по изменениям — 5 минут

Пути к реализации и нужному документу в запросе не указываем:

```bash
"$DEMO_BIN" --config "$DEMO_CONFIG" task \
  'Обнови существующую документацию по изменениям кода рабочей копии относительно HEAD. Сам посмотри diff, найди затронутое поведение и документы, прочитай связанный код и текущий текст, используй также смысловой поиск. Исправь только описание изменившегося поведения. Сохрани язык, структуру и несвязанные пользовательские правки. Новые Markdown-файлы не создавай.'
```

Скопируйте **новый** ID запуска:

```bash
export DEMO_DOCS_RUN='f3d54d4183aa441889eaeca927a557cc'
export DEMO_RUN_DIR="$DEMO_RUNS/$DEMO_DOCS_RUN"
cat "$DEMO_RUN_DIR/report.md"
cat "$DEMO_RUN_DIR/changes.patch"
git -C "$DEMO_OUTLINE" diff -- README.md
```

Ожидается `prepared`. Пока `git diff -- README.md` пуст: изменение документа находится только в подготовленном пакете.

Проверьте содержание:

- Меняется существующий раздел Debugging в README.
- Написано, что в development HTTP-логирование включено по умолчанию; для production остаётся включение через `DEBUG=http`.
- Условия `LOG_LEVEL` не отменены; формат логов и остальные разделы сохранены.
- Ассистент не меняет TypeScript и не создаёт дополнительных документов.

Пример смысла ожидаемой английской формулировки: “HTTP logging is enabled by default in development. In production, enable it by setting `DEBUG=http`.” Дословное совпадение не требуется; утверждения должны соответствовать прочитанному коду.

В `events.jsonl` проверьте `get_diff`, чтение `server/main.ts`, связанного `server/env.ts` и существующего README. При проверке уровней логирования полезен `server/logging/Logger.ts`. Один финальный ответ без реальных чтений не подтверждает выполнение сценария.

**Что сказать:** «Ассистент нашёл устаревший текст, сопоставил его с изменённым условием и подготовил точечную правку. До моего разрешения документ на диске остаётся прежним».

## 5. Применить и показать результат — 2 минуты

Если diff корректен, примените **пакет второго сценария**:

```bash
"$DEMO_BIN" --config "$DEMO_CONFIG" apply-run "$DEMO_DOCS_RUN"
git -C "$DEMO_OUTLINE" diff -- README.md server/main.ts
git -C "$DEMO_OUTLINE" status --short
```

Ожидается `applied`. В итоговом diff видны ваше изменение `server/main.ts` и обновление `README.md` ассистентом. Откройте README в редакторе — текст действительно изменился.

Покажите повтор той же команды:

```bash
"$DEMO_BIN" --config "$DEMO_CONFIG" apply-run "$DEMO_DOCS_RUN"
```

Ожидается `no_op: true`: готовый результат не применяется второй раз. `apply-run` не вызывает LLM и MCP; повторное исследование проекта не требуется. Если после preview изменились прочитанные файлы или HEAD, команда может вернуть `conflict`: сохраните свои правки и запустите новый анализ, не правьте хеши в manifest.

В конце оставьте демонстрационную ветку и два изменения для просмотра. Если они больше не нужны, вручную отмените только показанное условие и соответствующий фрагмент README после проверки diff. Не используйте `reset --hard` или `clean`; не удаляйте несвязанные правки. Коммит и публикация не входят в этот показ.

## Что считать успешной демонстрацией

| Сценарий | Видимый результат |
|---|---|
| Найти прямые импорты API | Два импорта `shallowEqual`, верные файлы/строки, реальное чтение/RAG и корректно расположенная таблица в preview |
| Обновить документацию | После изменения условия в `server/main.ts` самостоятельно найден и исправлен существующий README; preview просмотрен, пакет применён |

Если модель завершилась с `partial`/`failed`, пропустила `.tsx`, выдала `no_changes` при старом README или неверно описала поведение — этот запуск не прошёл демонстрацию. Покажите фактический статус и журнал, уточните задачу и повторите анализ. `prepared` подтверждает формальную готовность пакета, но требует смысловой проверки человеком. В предыдущем Outline-прогоне Qwen3 8B путала принадлежность примера файлу; проверочные ориентиры выше нужны именно для этого.

Если сохранился старый запуск `af8cb897a9a04d03a941977fa3d79a2e` со статусом `partial`, причина была в повторении диапазонов 5–233 и 5–200 при лимите чтения 200 строк. В текущем коде большие запросы читаются порциями с `next_read`. После обновления повторите команду `task` и используйте **новый** `run_id`; старый отчёт не изменится. Увеличение `mcp_timeout` эту ошибку не исправляет, применять старый частичный пакет нельзя.

Артефакты обоих запусков сохраняются в `$DEMO_RUNS/<run_id>/`: `manifest.json`, `events.jsonl`, `report.md`, `changes.patch`, `files/`, `originals/` и, после применения, `apply-journal.json`. Подробности механизма — в [FILE_TASKS.md](FILE_TASKS.md); предыдущие реальные проверки — в [отчёте Day 34](../evaluation/day34/REPORT.md).

**Обновление после пользовательского показа:** сценарий обновления HTTP-логирования теперь действительно проверен, но пока не прошёл проверку содержания. Были `partial` и формально `prepared` с правкой не того раздела или документа. Считайте шаги 3–5 воспроизведением задачи и критериями приёмки, а не готовым успешным показом. Не применяйте пакеты этих неудачных запусков. [Разбор и все повторы](../evaluation/day34/docs-demo-fix/REPORT.md).
