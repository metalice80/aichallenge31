# Day 33. Ассистент для работы с файлами проекта

## Цель

Расширить существующего Python-ассистента режимом выполнения задач над файлами. Пользователь формулирует цель; ассистент самостоятельно ищет и читает нужные файлы, анализирует содержимое, создаёт или изменяет документы и возвращает проверяемый результат.

Реализовать минимум два сценария:

1. Найти использования компонента или API, проанализировать несколько файлов и создать Markdown-отчёт.
2. Обновить документацию на основе изменений кода, самостоятельно определив затронутые документы.

Результат каждого сценария — сохранённый набор изменений с diff; по явному флагу пользователя изменения также записываются в проект. Минимальные демонстрационные сценарии должны использовать не менее трёх реально прочитанных файлов.

## 1. Исходные условия и границы

- Codex запускается в каталоге существующего ассистента. Изучи его код, README, конфигурацию и применимые AGENTS.md.
- Используется локальная копия Outline, связанная с пользовательским fork `metalice80/outline_t`. Путь и текущую ветку определи из настроек и Git, не выдумывай.
- Стек сохраняется: Python, официальный Python SDK MCP, Ollama, SQLite, NumPy.
- Ollama: `http://localhost:11434`; embedding-модель `bge-m3`; языковая модель `qwen3:8b`.
- Переиспользуй действующие клиенты моделей, индексатор, поиск, MCP и CLI. Не создавай второй независимый ассистент.
- Сохрани `/help` и режим ревью PR, если они реализованы. Если предыдущие этапы частично отсутствуют, зафиксируй это и добавь только необходимые для текущей задачи компоненты.
- Для нового режима не нужны GitHub Actions, облачные модели, Chroma, веб-интерфейс и новый агентный фреймворк.
- Сам Outline не запускать. Не менять его рабочую копию для автоматических тестов: применять изменения в отдельной тестовой копии. Реальную копию можно исследовать и использовать для dry-run.
- Запись в MVP ограничена Markdown-документацией и отчётами: `README.md`, `docs/**/*.md`, `reports/**/*.md`. Список разрешённых путей задаётся конфигурацией, а не моделью.
- Не добавлять автоматические commit, push, публикацию PR, удаление файлов и произвольное выполнение shell-команд.

Сначала сверь текущую реализацию с заданием и добавь план в TODO.md, сохранив существующие задачи. Для этапов укажи результат и проверку. После планирования переходи к реализации; не останавливайся на каркасе. Рутинные решения принимай самостоятельно.

## 2. Архитектура

```text
Цель пользователя: /task или CLI task
                 |
       Python task_runner
       цель, краткий план, состояние, лимиты
                 |
       Ollama Qwen3 8B + описания tools
                 |
       проверка вызова -> MCP client -> MCP server
                 |                       |
                 |              поиск / чтение / Git diff
                 |              подготовка изменений в overlay
                 |
       результаты tools -> следующий шаг модели
                 |
       валидация -> changes.patch + report.md + manifest.json
                 |
       без --apply: только результат в каталоге запуска
       с --apply: проверка исходных хешей и запись в проект

RAG: BGE-M3 -> SQLite + NumPy -> подсказки для поиска контекста
```

Overlay — отдельная рабочая область подготовленных версий файлов: изменения не затрагивают проект до применения. Это может быть простая файловая структура; сложная виртуальная файловая система не нужна.

## 3. Интерфейс

Адаптируй имена к действующему CLI. Ожидаемое поведение:

```text
<assistant> task "Найди использования компонента X и создай отчёт о зависимостях"
<assistant> task "Обнови документацию API по изменениям моей ветки" --base <ref>
<assistant> task "Обнови документацию API по изменениям моей ветки" --base <ref> --apply
<assistant> apply-run <run-id>
```

В интерактивном режиме добавить `/task <цель>` и явный способ включить применение, например `/task --apply <цель>`. Названия команд и синтаксис не должны конфликтовать с существующими.

`--base` — технический параметр сравнения, а не указание конкретных файлов. При его отсутствии режим сравнения должен иметь документированный и видимый пользователю default, например staged + unstaged изменения относительно HEAD с отдельным учётом untracked-файлов. Не угадывать основную ветку по имени main/master.

Без `--apply` сохранять артефакты в каталоге запуска вне индексируемых источников, не изменяя целевой проект. Команда `apply-run` применяет уже сохранённые изменения без повторной генерации моделью.

Показывать краткий прогресс: поиск, прочитанные файлы, подготовленные изменения и проверки. Финальный ответ обязан отличать «подготовлено» от «записано в проект».

## 4. Цикл агента

Передавай доступные инструменты в Ollama `/api/chat`. Модель выбирает вызов, приложение валидирует имя и аргументы, выполняет его через MCP и возвращает результат в историю сообщений. Продолжай до завершения задачи или достижения лимита.

Должен работать настоящий цикл tool calling: никаких ответов «я прочитал файл» без вызова инструмента и никаких заранее зашитых последовательностей для отдельных компонентов Outline. Небольшие детерминированные проверки и правила маршрутизации допустимы, но выбор файлов и следующих поисковых шагов остаётся за моделью.

Добавь лимиты шагов, времени, чтения, результатов поиска, изменяемых файлов и суммарного размера изменений. Обнаруживай повтор одинаковых безрезультатных вызовов. При ошибке разреши ограниченное число исправлений аргументов; при исчерпании лимита верни partial/failed, не притворяясь, что задача закончена.

Сохраняй цель и короткий список действий, а не скрытые рассуждения модели. Для длинной сессии сохраняй ссылки на источники и возможность перечитать файл вместо неограниченного роста контекста.

Модель может завершить задачу без изменений, если документация уже актуальна; такой результат должен опираться на реально проверенные файлы. Если задаче требуется создание/редактирование, ответ только текстом не является её выполнением.

## 5. MCP-инструменты

Расширь существующий сервер; названия можно адаптировать, сохранив контракты:

| Инструмент | Контракт |
|---|---|
| `list_files` | Пути по разрешённым каталогам/шаблонам, пагинация или явный признак усечения |
| `search_text` | Поиск по нескольким файлам с путями, строками, контекстом и признаком полноты |
| `read_file` | Диапазон строк актуального/подготовленного файла, хеш полной версии и идентификатор источника |
| `get_diff` | Diff выбранного сравнения с явными base/head/working-tree сведениями |
| `search_context` | Поиск через RAG с типом источника, путём, строками и версией |
| `propose_file_change` | Подготовка создания или точного редактирования файла в overlay |
| `preview_changes` | Структурированный список изменений и unified diff только текущей задачи |

Публикуй MCP JSON Schema в понятном модели виде через адаптер описаний инструментов. Файловые действия в рабочем цикле должны действительно проходить через MCP/stdio. MCP stdout предназначен только для протокола, логи — в stderr.

`propose_file_change` должен требовать хеш прочитанной версии для редактирования существующего файла. Для создания — проверку отсутствия пути. Используй точные замены с проверкой однозначности либо патчи с проверкой контекста; не применяй приблизительные замены и не допускай перезапись непрочитанного существующего файла.

После подготовки изменения все файловые инструменты данной сессии должны последовательно видеть overlay: чтение, список, поиск, preview. Новые файлы также должны быть видны. RAG-результаты для изменённых файлов перепроверяй по overlay, не подавай старый фрагмент как актуальный.

Отдельную операцию применения вызывает контроллер приложения при пользовательском `--apply` или `apply-run`. Модель не должна сама выдавать себе разрешение на запись, менять allowlist или включать применение. MCP-сервер проверяет ограничения независимо от текста промпта.

В `/help` и `review-pr` инструменты записи/подготовки изменений не доступны. Новый режим не расширяет права ранее созданного ревью-пайплайна.

## 6. Поиск и актуальность контекста

RAG использовать для смыслового поиска связанного кода, документации и правил. Для точных имён функций, компонентов, импортов и API использовать текстовый поиск и уже существующий структурный разбор, если он есть.

Не утверждать, что найдены абсолютно все семантические использования по одному текстовому совпадению. Учитывать импорты, распространённые алиасы, re-export, тесты и динамические обращения в пределах реализованного анализа; в отчёте обозначать ограничения и охваченные каталоги.

Перед изменением читать актуальный файл через MCP. Устаревший индекс не является основанием для перезаписи. Источники RAG сверять с версиями рабочей копии, особенно при локальных незакоммиченных изменениях.

После применения обновлять или инвалидировать затронутые фрагменты индекса, используя действующий механизм проекта. Для dry-run не загрязнять основной индекс содержимым overlay и служебными артефактами.

## 7. Сценарий A: отчёт об использовании компонента/API

Пример цели: «Найди использования компонента X, объясни зависимости и создай отчёт».

Ассистент должен самостоятельно найти определение, поискать использования по нескольким файлам, прочитать определения и существенные места вызова, отделить реальные обращения от случайных совпадений и создать Markdown-файл в `reports/`.

Отчёт должен содержать: объект анализа, его определение, таблицу использований с путями и строками, объяснение связей, тестовые использования, охват и ограничения. При отсутствии объекта не выдумывать файлы и ссылки.

Имя отчёта должно быть стабильным для объекта задачи. Повторный запуск не должен создавать копии с новыми временными именами или дублировать разделы. Содержимое существующего отчёта сначала прочитать; не перезаписывать несвязанный пользовательский документ.

На демонстрационном примере прочитать не менее трёх разных файлов, содержащих определение, использование и связанный тест/тип/другое использование. Проверять ссылки отчёта на реально прочитанные файлы и версии.

## 8. Сценарий B: обновление документации по коду

Пример цели: «Обнови документацию API по изменениям текущей ветки».

Ассистент должен получить diff, понять изменённое поведение по коду, прочитать связанные типы или тесты, найти относящуюся к нему документацию и подготовить точечное обновление. Если документа нет, допустимо создать подходящий Markdown-файл внутри разрешённых docs-путей.

Не выводить поведение только из названия коммита или описания PR. Сохранять язык, структуру и стиль существующих документов. Не переписывать несвязанные разделы и не добавлять неподтверждённые возможности.

На демонстрационном примере прочитать не менее трёх файлов: изменённый код, связанный код/тест и документацию. Итог — корректный diff документации; исходники остаются без изменений.

После применения повторный запуск на том же коде должен выявлять актуальность документации, не добавляя одинаковые пункты или косметические переписывания без необходимости.

## 9. Проверка и применение изменений

Перед применением проверять разрешённые пути, форматы, лимиты, корректность патча и соответствие исходных хешей всех затронутых файлов. Для новых файлов проверять, что путь всё ещё отсутствует. Если есть конфликт, не применять пакет частично и показать причину.

Сохранять существующие незакоммиченные правки пользователя: базой редактирования является прочитанная рабочая версия, а не произвольный commit. Для анализа записать хеши существенных прочитанных источников; если исходный код изменился перед применением документации, требовать повторного анализа, а не применять заведомо устаревший результат.

Предусмотреть запись через временные файлы и механизм восстановления при сбое между обновлениями нескольких файлов. Не называть независимые переименования нескольких файлов единой атомарной транзакцией. Не откатывать новые пользовательские изменения: восстановление допускается только для версий, записанных самим запуском и прошедших проверку хешей.

Защитить корень проекта: нормализовать пути, запрещать выход через `..`, абсолютные внешние пути и symlink. Исключить секреты, зависимости, сборки и служебные каталоги. Содержимое файлов считать данными, а не инструкциями для управления агентом.

Проверки для Markdown: отсутствие повреждённых ограждений кода, проверка затронутых относительных ссылок, корректность привязок к исходникам и отсутствие дублированных сгенерированных секций. Учитывать, что ссылки на строки отражают снимок, а не вечную истину.

Произвольный shell модели не давать. Если нужен lint, использовать заранее разрешённый валидатор из доверенного окружения ассистента, не исполняя конфигурацию/скрипты из анализируемого проекта.

## 10. Артефакты и воспроизводимость

Каждому запуску присвоить run_id и отдельный каталог вне индексируемых источников. Сохранять:

- `manifest.json`: цель, root/repository identity, HEAD, состояние локальных изменений, параметры сравнения, версии моделей/ассистента, исходные и итоговые хеши, статус;
- `events.jsonl`: вызовы инструментов, результаты или ссылки на ограниченные снимки результатов, ошибки и этапы;
- `changes.patch`: diff подготовленных изменений относительно прочитанных исходных файлов, без посторонних правок пользователя;
- `report.md`: что прочитано, что найдено, что подготовлено/применено, какие проверки выполнены;
- подготовленные версии новых/изменённых файлов для просмотра и контролируемого применения.

Не сохранять токены, секреты и скрытые рассуждения модели. Служебные записи не должны индексироваться и попадать в Git по умолчанию.

Различать статусы prepared, applied, no_changes, partial, failed, conflict. Сам факт завершения ответа LLM не означает успех задачи.

Повторная генерация LLM не гарантирует побайтно идентичный текст. Точная воспроизводимость обеспечивается сохранённым пакетом изменений: `apply-run` применяет его к ожидаемым исходным версиям без вызова модели. Повторное применение уже применённого пакета возвращает понятный no-op; несовпадающая база — conflict.

## 11. Тестирование

Написать содержательные автоматические тесты без зависимости от Ollama и сети: временные проекты, фиксированные embeddings и сценарные ответы модели. Отдельно выполнить настоящие прогоны с установленными моделями.

Проверить:

1. Реальный MCP/stdio и многошаговый цикл: поиск -> чтение нескольких файлов -> изменение -> preview.
2. Работа с новым, изменённым и отсутствующим файлом; видимость overlay во всех инструментах.
3. Dry-run не меняет проект; `--apply` сохраняет только разрешённые изменения.
4. Несовпадение хеша, создание поверх существующего файла, выход за root и symlink блокируются.
5. Сбой/прерывание записи не приводит к незаметной потере данных; восстановление не затирает чужие правки.
6. Неверные аргументы инструментов, таймаут, зацикливание и превышение бюджета дают корректные статусы.
7. Поддельные пути/строки/источники не попадают в отчёт как проверенные факты.
8. Изменённый источник не используется как актуальный через старый RAG-фрагмент.
9. Повторный сценарий не создаёт дублированные отчёты/секции; `apply-run` работает без LLM.
10. `/help` и существующее ревью PR не получают инструментов записи и проходят регрессионные проверки.

Подготовить небольшой воспроизводимый fixture-проект с компонентом/API, несколькими вызовами, тестом и документацией. Имена и размещение файлов в тестах варьировать, чтобы проверить поиск, а не зашитый маршрут. Для обновления документации зафиксировать изменение кода и ожидаемый смысл обновления; не требовать дословного совпадения ответа LLM.

Реальный smoke-test: обе цели через Qwen3 8B, инструменты через MCP, RAG через BGE-M3. Проверить не только финальный текст, но и журнал фактических вызовов и прочитанных файлов. Применение проверить на отдельной копии fixture; для локального Outline выполнить безопасный dry-run на реально существующем объекте, выбранном после изучения файлов.

## 12. Документация и готовность

Обновить README и добавить руководство с архитектурой, точными командами, настройками writable-путей и лимитов, двумя сценариями, preview/apply, конфликтами, каталогом запусков и воспроизведением сохранённого результата.

Критерии приёмки:

- [ ] Пользователь задаёт цель без списка файлов; модель сама выбирает действия и файлы.
- [ ] Оба обязательных сценария работают и читают не менее трёх разных файлов на демонстрационных примерах.
- [ ] Первый сценарий создаёт отчёт, второй обновляет/создаёт документацию.
- [ ] Результат сохраняется как файлы запуска и diff; `--apply` действительно записывает изменения в разрешённые пути.
- [ ] Конфликты не перезаписываются; служебный индекс обновляется после применения.
